# AquaBalance: viva preparation

_Generated 2026-10-14 from the project's result files. Numbers match `final_results_summary.md`._

> This is a simulation-based decision-support prototype, not autonomous real-world utility control. All data in this project is synthetic: it comes only from EPANET simulations run through WNTR. No real utility data is used.

## 30-second explanation

AquaBalance is a simulation-based decision-support prototype for a small water-distribution network. I use EPANET, through the WNTR Python package, to simulate 300 scenarios: normal days, high demand, leaks, a blocked pipe, a mis-set valve. A GRU neural network forecasts the pressure at three junctions 15 minutes ahead. A transparent rule engine turns the forecast into a risk label, a bounded recommender suggests a small pump or valve change, and EPANET re-simulates that change to check it is safe. Everything is synthetic, so it is a prototype, not a control system.

## 60-second explanation

Water networks need pressure inside a safe band: too low and customers, especially a hospital, lose supply; too high and pipes leak or burst. Real operators react after the problem appears. AquaBalance tries to warn earlier. Step one: EPANET/WNTR generates 300 labelled-by-physics scenarios, so I have ground truth without real data. Step two: I split them by whole scenario, never by row, so the test set is truly unseen, and train a GRU on the last 3 hours of sensor and pump/valve values to predict J2, J3 and J4 pressure 15 minutes ahead. I compare it fairly with persistence, a random forest, an LSTM and a small TCN. Step three: a rule-based risk engine classifies the forecast (low, high, imbalance, leak-like) and treats the hospital node J4 as most important. Step four: a recommendation engine proposes a bounded pump or valve change and, for leaks, only an inspection. Step five: every recommendation is re-run in EPANET before and after, and rejected if any node gets worse or J4 is sacrificed. Result: on test scenarios the best forecaster was Random Forest (MAE 0.065 m); the GRU reached 0.103 m, better than persistence (0.131 m) but not better than the random forest (0.065 m). Of 23 validated recommendations, 11 improved the simulated network, and the rest were no-action, inspection or "no safe action". The limits are clear: synthetic data, tiny network, validation inside the same simulator.

## Ten likely questions and concise answers

**1. Why did you use EPANET (and WNTR)?**  
I have no real utility data, and real faults cannot be created on demand. EPANET is the standard, physics-based hydraulic solver, so its pressures and flows follow real hydraulics. WNTR lets me script thousands of reproducible scenarios, replay any one exactly, and re-run a recommended action to validate it. It gives labelled ground truth and a safe testbed. The price is that it is a simulation.

**2. Why did you use a GRU?**  
The task is sequence-to-value: the last 3 hours of pressure, flow, demand and pump/valve values predict the next pressure. A GRU is a compact recurrent network that remembers recent trends, with about the same number of parameters as the LSTM I compared it with (26,691 vs 26,723) and runs fast. It is a justified starting point for time-series forecasting. But I tested it honestly: it beat persistence yet not the random forest on this small task (GRU 0.103 m vs forest 0.065 m), and the TCN/LSTM comparison is in the results. The deep-learning value here is a comparison and a path to richer data, not a proven win.

**3. What is the difference between sensors and actuators in your project?**  
Sensors measure: junction pressures, pipe flows, demand, and the reported pump speed and valve setting. They feed the model. Actuators change the network: the pump (speed) and the pressure-reducing valve (setting). In AquaBalance the model only reads sensor-type values, and the recommendation engine only SUGGESTS an actuator change inside the simulation. Nothing is connected to real equipment, and an operator would approve any change.

**4. What is the limitation of simulation data?**  
It is clean, small and generated by my own assumptions. There is no sensor noise by default, no missing data, no unknown demand or valve states, and the fault families are idealised. Validation uses the same simulator that made the data, so it is optimistic. Results show the method works in simulation; they do not show it works on a real utility.

**5. Pressure imbalance versus equal pressure: what is the difference?**  
I do not try to make all junctions equal. Elevation and demand differ, so natural pressures differ. A pressure imbalance means the spread between the highest and lowest of J2, J3, J4 exceeds 20 m, even if each node is inside the 20-60 m band. Safe operation means every node inside its band (J4, the hospital, at least 30 m) and the spread under the limit. Equal pressure is not the goal.

**6. How did you prevent data leakage?**  
I split by whole scenario ID, so no window of a test scenario is in training. Windows are cut inside one scenario. Scalers are fitted on training scenarios only. Hidden truth (scenario type, leak flag, leak size) is never a model input, and a test checks it. The EPANET validation reads only the sensor-style history.

**7. Did the GRU beat your baselines?**  
Partly. Test MAE: persistence 0.131 m, GRU 0.103 m, random forest 0.065 m, LSTM 0.105 m, TCN 0.088 m. The GRU beat persistence but the forest was best on error. Over extra seeds the spread (std) of test MAE was GRU 0.0024, LSTM 0.0015, TCN 0.0010 m, so only gaps clearly larger than that mean something. I report this as it is rather than claim superiority.

**8. How does the recommendation engine stay safe?**  
Changes are bounded (pump about ±10 %, valve about ±15 %) and small. J4 is protected first: no action may push it toward its minimum. Leak-like and burst-like patterns only give an inspection recommendation. Every suggestion is re-run in EPANET; if no candidate is safe the answer is "No safe action found; operator inspection recommended.".

**9. What does your EPANET validation prove, and what does it not?**  
It proves that in the simulated network the chosen action improved (or did not worsen) the next hour's pressures under my safety rules. This validates the recommendation in the simulated EPANET network. It is not field validation in an actual water utility. It does not prove field performance, because the real system has noise, delays, unknown states and other equipment.

**10. What would you need to deploy this for real?**  
Real SCADA data and calibrated hydraulic models, physical pressure and flow sensors with noise handling, an actuator interface with safety interlocks, much longer testing, and an operator-in-the-loop workflow where a human approves every change. Future research: graph-temporal neural networks that use the pipe topology, reinforcement learning for control inside the validated simulator, and validation on real utility data.

## Short answers to follow-up questions

- **How is a leak detected?** Mass balance: water entering the network minus the metered demand should be near zero; a persistent positive gap with a pressure drop means leak-like. It is flagged for inspection only.
- **Why is J4 special?** It represents a hospital / critical service, so it has a stricter minimum and is never sacrificed to improve another node.
- **Why rule-based risk rather than a neural classifier?** Operators must be able to see why an alert was raised; thresholds are explicit and configurable.
- **Why is a random forest good here?** Pressure changes slowly, so recent values and differences carry most of the signal; trees on engineered lag/rolling features capture it with little data.
